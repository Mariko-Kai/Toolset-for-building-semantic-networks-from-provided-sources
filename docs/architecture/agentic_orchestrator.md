# Агентная архитектура: от линейного конвейера к оркестратору с мониторингом

> Исследование (запрошено на Этапе 4). Отвечает на вопрос: **как перейти от
> жёсткого линейного конвейера к гибкой агентной системе с плотным мониторингом
> состояния и оркестратором верхнего уровня, который реагирует на отклонения,
> расследует инциденты, готовит план патча и — после подтверждения человеком —
> применяет исправление/расширение архитектуры.**
>
> Документ задаёт целевую модель и поэтапную, безопасную миграцию. Этап 4 строит
> её субстрат (узлы со статусами, состояние, оркестратор, реестры), не ломая
> текущий конвейер.

## 1. Что не так с текущим конвейером

`pipeline/ollama_wrapper.run_enrichment_pipeline` — жёсткая линейная цепочка:

```python
steps = [("1/3", extract, [...]), ("2/3", align, [...]), ("3/3", synth, [...])]
for step in steps:
    proc = subprocess.Popen(...)
    for line in proc.stdout:           # ← мониторинг = парсинг stdout
        if "[synthesizer] Parsed: entity_id=" in line: ...   # магические строки
    if proc.returncode != 0: return False, [], {}            # ← статус = только код возврата
```

Проблемы для агентного развития:
1. **Нет наблюдаемости.** Единственный сигнал — returncode и регэкспы по логам.
   Нельзя отличить «норму» от «отклонения», нет метрик, нет истории.
2. **Жёсткая последовательность.** Добавить шаг/ветку/повтор = править главный цикл.
3. **Нет реакции на аномалии.** Любой сбой → `return False`. Нет расследования,
   нет плана, нет точки вмешательства человека.
4. **Связь через stdout.** Хрупкий контракт; меняется формат лога — ломается парсинг.

## 2. Целевая модель (четыре слоя)

```
┌────────────────────────────────────────────────────────────────┐
│  Orchestrator (верхний уровень)                                  │
│  • гоняет поток узлов, наблюдает статусы, применяет политики      │
│  • при отклонении → Incident → расследование → план → подтвержд. │
└───────────────┬───────────────────────────┬─────────────────────┘
                │                             │
        ┌───────▼────────┐          ┌─────────▼──────────┐
        │  RunState +    │          │ IncidentHandler    │
        │  EventLog      │◄─────────│ (агент: код-ревью,  │
        │ (мониторинг)   │          │  root-cause, план)  │
        └───────┬────────┘          └─────────┬──────────┘
                │                             │ PatchPlan
        ┌───────▼─────────────────────────────▼──────────┐
        │  Nodes (узлы) — реестр @register_node           │
        │  extract │ align │ synth │ lean │ promote │ ...  │
        │  каждый: run(ctx) -> NodeResult(status,out,…)    │
        └─────────────────────────────────────────────────┘
```

### Слой 1 — Узлы (Nodes)
Единица работы с **типизированным контрактом** вместо парсинга stdout:

```python
@register_node("synth")
class SynthNode(Node):
    name = "synth"
    def run(self, ctx: NodeContext) -> NodeResult: ...
```

`NodeResult` несёт: `status` (enum), структурный `output`, `metrics` (тайминги,
счётчики), `events` (что произошло), `signals` (напр. «не хватает зависимости X»,
«низкая уверенность»). Существующие модули (`ensemble_extractor`,
`canonical_synthesizer.promote_cluster`, `export_to_lean`, `validator`) оборачиваются
узлами-адаптерами — **без переписывания**.

`NodeStatus`: `OK | DEVIATION | FAILED | NEEDS_INPUT | SKIPPED`.
- `DEVIATION` — отработал, но вне «нормального коридора» (напр. синтез вернул 0
  сущностей, Lean-валидация у́же таймаута, доля `sorry` выше порога).
- `NEEDS_INPUT` — требуется решение/подтверждение человека.

### Слой 2 — Состояние и мониторинг (RunState + EventLog)
Единый источник истины о прогоне: история запусков узлов, текущие статусы,
переходы, **append-only EventLog**, агрегированное «здоровье». Персистится в
канонической БД (Этап 2) — переживает падения, доступен для live-инспекции.

«Отклонение от нормы» формализуется **коридором ожиданий** узла (декларативно, в
конфиге/данных): допустимые статусы, пороги метрик. Монитор сравнивает факт с
коридором → ставит `DEVIATION`. Именно ради этого слоя Этап 4 вводит структурный
I/O: по `NodeResult.status` + метрикам можно мониторить, по stdout — нет.

### Слой 3 — Оркестратор
Гоняет поток (последовательность или DAG узлов), после каждого узла обновляет
RunState, применяет **политику**:
- `OK` → дальше;
- транзиентная ошибка → ретрай с backoff (механика из Этапа 1);
- `DEVIATION`/исчерпанные ретраи/структурный сбой → **поднять Incident** и передать
  управление в цикл обработки инцидента (а не слепо продолжать/падать).

Поток узлов и пороги задаются конфигом — добавление узла/ветки не трогает ядро.

### Слой 4 — Обработка инцидентов (агентная часть)
`Incident` — структурная запись: узел-триггер, статус, захваченный контекст (входы,
выходы, события, ссылки на релевантный код/логи), серьёзность.

`IncidentHandler` — интерфейс:
```python
class IncidentHandler(Protocol):
    def investigate(self, incident: Incident) -> Investigation: ...
    def propose_patch(self, investigation: Investigation) -> PatchPlan: ...
```
Агентная реализация (LLM-агент уровня Claude): читает контекст инцидента, проводит
**точечный код-ревью** причастного узла/модуля, выявляет первопричину, формирует
`PatchPlan` (файлы, диффы, обоснование, тесты, риск).

**Обязательный gate человека:** оркестратор показывает `PatchPlan` и **ставит прогон
на паузу**. Только после явного подтверждения пользователя патч применяется —
через тот же безопасный поток: ветка git → применение → полный прогон тестов →
коммит. Это формализация того ручного цикла (ревью → план → подтверждение →
применение → тесты), которым ведётся текущий рефакторинг.

## 3. Как это ложится на репозиторий и Этап 4

| Целевой элемент | Где живёт | Связь с этапами |
|---|---|---|
| `Node`/`NodeResult`/`NodeStatus` + реестр | `pipeline/nodes/` | **4.1** |
| Адаптеры существующих модулей в узлы | `pipeline/nodes/adapters.py` | 4.1 (постепенно) |
| `RunState`, `EventLog`, `Orchestrator` | `pipeline/orchestration/` | **4.1b** |
| `Incident`, `IncidentHandler`, gate подтверждения | `pipeline/orchestration/incidents.py` | 4.1b (скелет) |
| Персистенция прогонов/инцидентов | таблицы `run`,`run_event`,`incident`,`patch_plan` в канон. БД | переиспользует Этап 2 |
| Монитор-UI (live состояние, поток событий, кнопки подтвердить/отклонить) | `web/` (WebSocket уже есть) | переиспользует Этап 2.5 |
| Реестры типов/хинтов (поведение в данных) | `pipeline/registries/` | **4.2** |
| Внешние промпты | `pipeline/prompts/` | **4.3** |
| Типизированный конфиг + политики/коридоры | `pipeline/config` | **4.4** |
| Узлы как «возможности»/доменные пакеты (вкл. OCR) | `mathesis/capabilities`, `mathesis/domains` | Этап 5 |

Ключевой принцип: **узел — общая абстракция и для конвейера, и для агентной
системы, и для capabilities Этапа 5.** Оркестратор не знает про «математику» —
он знает про узлы, статусы и политики. Это и есть переносимость на другие задачи.

## 4. Безопасность самоизменяющейся системы

Система, которая правит собственный код, требует жёстких рамок:
1. **Подтверждение человека обязательно** перед любым применением патча/расширения.
2. **Каждый патч — через git-ветку и полный прогон тестов** (харнесс Этапов 0–3).
3. **Патч — это читаемый дифф**, никогда не «непрозрачное» изменение; ревью обязательно.
4. **Расширение, а не мутация ядра**: оркестратор предлагает новые узлы/возможности
   и регистрирует их явно; не переписывает оркестратор «на лету».
5. **Dry-run везде** (паттерн из Этапа 1.4): сначала показать эффект, потом применять.
6. **Аудит**: EventLog + сохранённые Incident/PatchPlan — полная трассируемость, кто
   что и почему изменил.

## 5. Поэтапная миграция (низкий риск)

1. **4.1** Контракт узла + `NodeResult` + реестр. Обернуть текущие 3 шага узлами;
   передачу данных перевести со stdout-магии на структурный handoff (temp-JSON —
   уже так логируется `ParsedDeps`).
2. **4.1b** `RunState`+`EventLog`+`Orchestrator`, гоняющий узлы и пишущий состояние.
   Сначала просто наблюдает и поднимает статусы. Затем — `Incident` + gate
   подтверждения (скелет; LLM-расследование подключается позже как реализация
   `IncidentHandler`).
3. **4.2–4.4** Реестры (типы/хинты), внешние промпты, типизированный конфиг с
   коридорами/политиками — чтобы поведение и пороги менялись данными, а узлы/потоки
   расширялись без правки ядра.
4. **Этап 5** OCR и прочее — как подключаемые узлы-возможности; агентный
   `IncidentHandler` — как LLM-агент с код-ревью и планированием патчей.

Текущий `run_enrichment_pipeline` остаётся рабочим на всё время миграции: узлы
сначала оборачивают его шаги, оркестратор запускается параллельно как
наблюдатель, и только потом становится основным драйвером.
