## 0. Контекст и зафиксированные решения

По итогам код-ревью (см. историю обсуждения) и ответов заказчика приняты решения:

| Решение | Значение | Следствие для ТЗ |
|---|---|---|
| **Платформа** | Windows + Linux | Управление процессами через `psutil` (kill дерева), без POSIX-only сигналов; пути только через `pathlib`. |
| **Каноническая модель** | Единый граф сущностей с осью **Lean `def`/`prop`** (+`axiom`). Сильная привязка к представлениям Lean. | Схему `entities` формализуем и обогащаем; ветвистую таксономию `object/property/operation/theorem/axiom` сворачиваем в `kind` + типизированные рёбра. Слой `mathesis/` переписываем как типизированный API над единой схемой. |
| **Данные в `db/`** | Можно пересоздавать | Источник истины — `content/*.tex` + повторная экстракция. Пишем чистые init/seed/migration-скрипты, без бережной миграции legacy-строк. |
| **Формат ТЗ** | Детальный файл | Этот документ. |

### Принципы, которым подчинён весь рефактор
1. **Один источник истины** на каждый аспект: одна БД-схема, один путь к БД, один конфиг, один реестр стадий.
2. **Доменные знания — в данных, не в коде.** Словари, типы, хинты ошибок Lean, промпты — выносятся из `if/elif` в реестры/файлы. Это основа целей «дописывать недостающий функционал» и «переносить архитектуру на другие задачи».
3. **Границы и таймауты на всё внешнее.** Ни один подпроцесс/HTTP-вызов не может висеть бесконечно.
4. **Структурный I/O между стадиями** (JSON/dataclass), а не парсинг stdout по магическим строкам.
5. **Ошибки не глотаются.** Возврат `""` при сбое запрещён — либо исключение, либо типизированный результат `Result`.
6. **Каждый рефактор прикрыт тестом.** Сначала тест на текущее поведение чистой логики, потом изменение.
7. **Вызовы ИИ — за абстракцией и замокированы в тестах.** Производительность меряем без учёта LLM.

### Глобальные критерии готовности проекта (Definition of Done)
- [ ] `pip install -e .[dev]` ставит проект и dev-зависимости; `pytest` зелёный.
- [ ] `ruff check .` без ошибок на `mathesis/`, `pipeline/`, `tools/`, `web/`, `tests/`.
- [ ] Один путь к БД из конфига; `db/mathesis.db` и корневой `mathesis_index.db` удалены/в `.gitignore`.
- [ ] `.venv/` вычищен из git-индекса.
- [ ] Полный прогон конвейера на 1 термине не зависает и завершается с понятным статусом даже при недоступном Ollama/Lean.
- [ ] Документация (`docs/`) описывает фактическую архитектуру, а не идеализированную.

## Этап 1 — Стабильность подпроцессов и конвейера

**Цель:** устранить корневые причины зависаний и OOM (а не симптомы). После этапа конвейер
переживает недоступность Ollama/Lean и не зацикливается.

### 1.1 Единый модуль управления процессами
- **Мотивация:** Lean REPL и llama.cpp-сервер запускаются/убиваются по-разному, без kill дерева; на Windows плодятся осиротевшие процессы.
- **Файлы:** новый `mathesis/proc.py`; потребители — `pipeline/lean_validator.py`, `pipeline/hybrid_search.py`.
- **Что сделать:**
  - `managed_process(cmd, ...)` — контекст-менеджер: запуск, `terminate→kill` дерева через `psutil.Process(pid).children(recursive=True)`, гарантированная очистка в `finally`.
  - `read_with_timeout(pipe, timeout)` — кроссплатформенно (поток-ридер + `queue`), без `signal.alarm`.
- **Приёмка:** unit-тест запускает дочерний процесс, спавнящий внука; после выхода из контекста оба мертвы (проверка через psutil).

### 1.2 Надёжный Lean REPL
- **Мотивация:** singleton переиспользуется; порча состояния → тихие пустые ошибки; нет таймаута транзакции.
- **Файл:** `pipeline/lean_validator.py`.
- **Что сделать:**
  - Таймаут на цикл запрос-ответ (из 1.1).
  - Детекция «отравленного» состояния: при таймауте/исключении/`poll()!=None` — убить дерево и пересоздать инстанс при следующем `get()`.
  - Различать `success`/`failed`/`timeout`/`crashed` в результате (сейчас всё схлопывается в `failed`).
  - Убрать зависимость от снятия `maxHeartbeats` как от единственной защиты (оставить как доп. меру).
- **Приёмка:** тесты: (а) валидный Lean → `success`; (б) битый Lean → `failed` с сообщением; (в) «зависший» REPL → `timeout` за ~таймаут, следующий вызов работает (REPL пересоздан).

### 1.3 Ограничители циклов конвейера
- **Мотивация:** очереди `synthesis_queue`/`validation_queue` могут зациклить сущность бесконечно; ретраи синтеза без backoff (до 9 вызовов, `sleep(2)`).

- **Что сделать:**

  - Экспоненциальный backoff вместо фиксированного `sleep`; общий бюджет времени на кластер.
  - Детектор повторяющейся ошибки (одинаковый feedback дважды → прекратить попытки).
- **Приёмка:** тест с фейк-LLM, всегда возвращающим невалидный результат, завершается за конечное число итераций, статус «failed», без зависания.

## Этап 2 — Консолидация модели данных (фундамент развития)

**Цель:** один канонический слой данных, выстроенный вокруг Lean-дихотомии `def`/`prop`/`axiom`.
Это центральный этап: от него зависят расширяемость и перенос на другие домены.

### 2.1 Спроектировать и зафиксировать каноническую схему
- **Мотивация:** сейчас две несовместимые схемы в разных файлах БД; `mathesis/` и `pipeline/` не синхронизированы.
- **Файлы:** новый `mathesis/schema.py` (единый `SCHEMA_SQL` + версия), `docs/architecture/data_model.md`.
- **Целевая схема (спина = Lean):**
  - `entity`:
    - `id TEXT PK` (slug, напр. `def-real-analysis-limit`)
    - `kind TEXT CHECK(kind IN ('def','prop'))` — **строго бинарная ось Lean (def / prop)**.
      Отдельного вида `axiom` НЕТ: аксиомы вносятся как `def` (постулируют объект/структуру)
      или `prop` (постулируют утверждение) — по контексту.
    - `lean_decl TEXT` — конкретная форма Lean-декларации (`def|abbrev|structure|class|instance|theorem|lemma|axiom`).
      «Аксиоматичность» (постулируется без доказательства) выражается здесь: `lean_decl='axiom'`
      на prop-сущности — а не отдельным видом в графе знаний.
    - `title TEXT`, `module TEXT`, `nl_desc TEXT`
    - `latex TEXT` (канонический формальный LaTeX)
    - `lean_code TEXT`, `lean_status TEXT CHECK(... IN ('unvalidated','valid','sorry','failed'))`
    - `tex_path TEXT`, `lean_path TEXT` (файлы — источник истины контента)
    - `embedding BLOB`, `created_at`, `updated_at`
  - `alias(alias TEXT PK, entity_id TEXT FK)` — мультиязычный O(1) lookup.
  - `entity_source(id, entity_id FK, source_book, page_info, discipline)` — провенанс.
  - `entity_dependency(source_id FK, target_id FK, role, proof_step, PK(source_id,target_id,role))`,
    `role IN ('uses','generalizes','instance_of','proof_uses','component')` — типизированные рёбра (сворачивают theorem_object/property/operation/dependency в один граф).
  - `equivalence(a_id, b_id, proof_id FK NULL, PK(a_id,b_id), CHECK(a_id < b_id))`.
  - `entity_fts` — FTS5 по `title, nl_desc, latex` (`unicode61`).
  - **Индексы** на `entity.kind`, `entity.module`, FK-колонки рёбер/источников.
- **Staging (отдельный жизненный цикл, можно очищать):** `raw_formulation` (бывший `formulation_raw_cache`), `cluster_entity_map`, `pending_edges`.
- **Приёмка:** `docs/architecture/data_model.md` с ER-описанием и маппингом старых таксономий
  (object/operation → `kind=def`; theorem/lemma/property → `kind=prop`; аксиома → `def`|`prop`
  с `lean_decl='axiom'` при необходимости); ревью схемы.

### 2.2 Слой доступа `mathesis/` как типизированный API над единой схемой
- **Мотивация:** объединить два слоя в один источник истины с типобезопасным API.
- **Файлы:** `mathesis/db.py` (connection: WAL, FK, единый путь из конфига), `mathesis/models.py` (dataclasses `Entity`, `Dependency`, `Source`, `Equivalence`; enum'ы `Kind`, `LeanDecl`, `DepRole`, `LeanStatus`), `mathesis/repo.py` (CRUD + граф), `mathesis/validator.py` (целостность).
- **Что сделать:**
  - CRUD по `entity`/рёбрам с валидацией enum на входе.
  - Граф: `trace_to_roots` (recursive CTE; трассировка обрывается на аксиоматичных
    сущностях `lean_decl='axiom'` или листьях DAG — отдельного вида `axiom` нет),
    `get_used_by` (через `set`, без питоновского `any()`), `get_full_dag`.
  - FTS-поиск с пагинацией.
  - Валидатор: битые ссылки, циклы (Tarjan SCC вместо рекурсивного DFS), сироты, учёт `sorry`/`lean_status`.
  - Убрать дубль `IndexError` (→ `MathesisIndexError`).
- **Приёмка:** unit-тесты на CRUD, трассировку к аксиомам, поиск, детекцию циклов на синтетическом графе.

### 2.3 Единый путь к БД и пересоздание
- **Файлы:** `pipeline/config.py` (поле `db_path`), `pipeline/init_db.py` → тонкая обёртка над `mathesis.schema`, `pipeline/reseed_db.py`, `pipeline/actualize_db.py`.

- **Приёмка:** свежий `init_db` + `actualize_db` на `content/` собирает БД без ошибок; `web/app.py` и конвейер читают одну БД.

### 2.4 Staging → Promotion
- **Мотивация:** разделить «грязную» экстракцию и «чистый» канон.
- **Файлы:** `pipeline/ensemble_extractor.py` (пишет в `raw_formulation`), `pipeline/canonical_synthesizer.py` (кластер → промоушен в `entity`).
- **Что сделать:** явная функция `promote_cluster(cluster_id) -> entity_id`, идемпотентная; экстракция не трогает канонические таблицы напрямую.
- **Приёмка:** тест: прогон staging→promotion на фикстуре создаёт корректную каноническую сущность с рёбрами и провенансом.

### 2.5 Привести `web/app.py` к новому API
- **Файлы:** `web/app.py`, шаблоны (минимально).
- **Что сделать:** переключить чтения на `mathesis.repo`; глобальное мутабельное состояние компилятора защитить (lock) — частично.
- **Приёмка:** веб-каталог и поиск работают на единой БД.

**Выход Этапа 2:** один канонический слой данных, выровненный с Lean; `pipeline/` пишет через staging→promotion; `mathesis/` — типизированный фасад; БД пересоздаётся из `content/`.

## Этап 3 — Производительность (без учёта вызовов ИИ)

**Цель:** убрать алгоритмическую неэффективность вокруг ИИ и в работе с данными/файлами.

### 3.1 Батч-эмбеддинги и матричное сходство
- **Мотивация:** `postprocess_equivalence.py:544` и `update_embeddings.py` считают эмбеддинги по одному в цикле; затем O(n²) попарный косинус питоном.
- **Файлы:** `pipeline/postprocess_equivalence.py`, `pipeline/update_embeddings.py`, `pipeline/model_manager.py` (batch API).
- **Что сделать:** батч-запрос эмбеддингов; нормировать и считать `S = X @ X.T` (numpy уже есть, 2.4.4); кэш эмбеддингов в БД с инвалидизацией по хешу текста; чекпойнты при массовом пересчёте.
- **Приёмка:** бенч на N=300 синтетических сущностей: время дедупа (без учёта самих LLM-вызовов) падает на порядок; результаты совпадают со старой реализацией на фикстуре.

### 3.2 Векторный индекс для резолва сущностей
- **Мотивация:** линейный скан всех эмбеддингов на каждый запрос.
- **Файлы:** `pipeline/ollama_wrapper.py` (резолв), новый `pipeline/vector_index.py`.
- **Что сделать:** предзагруженная numpy-матрица + топ-k через argpartition (или `hnswlib`, если оправдано). Нормализацию заголовков считать один раз и кэшировать.
- **Приёмка:** бенч резолва на N=1000: сублинейно/однопроходно; корректность top-k на фикстуре.

### 3.3 Однопроходное сканирование PDF

## Этап 5 — Обобщение и «самодостраивающаяся» архитектура

**Цель:** реализовать стратегические цели — архитектура достраивает недостающие представления и
применима за пределами математики. Делается только после стабильной базы (Этапы 0–4).

### 5.1 Абстракция «доменного пакета» (Domain Pack)
- **Мотивация:** доменные знания (стеммеры, словари, типы, целевой формальный язык) должны подключаться, а не быть вшиты в математику/Lean.
- **Файлы:** новый `mathesis/domains/` (`base.py`: интерфейс `DomainPack` — токенизация/стемминг, типы сущностей, целевой бэкенд формализации, правила валидации), `mathesis/domains/math_lean/` (текущая математика+Lean как первый пакет).
- **Приёмка:** конвейер параметризуется доменным пакетом; математика работает как пакет; описан контракт для второго домена.

### 5.2 Реестр «возможностей» (capabilities) и достройка представлений
- **Мотивация:** цель «дописывать функционал для объектов, которые иначе нельзя сохранить» — нужен механизм, который при отсутствии представления (напр. Lean-декларации для нового вида объекта) синтезирует недостающую часть по реестру стратегий.
- **Файлы:** `mathesis/capabilities/` (реестр `capability → стратегия синтеза`), интеграция в промоушен (2.4) и Lean-экспорт.
- **Что сделать:** при промоушене проверять, покрыт ли объект существующими представлениями; если нет — выбрать/синтезировать стратегию (новый макрос, новый Lean-паттерн) и зарегистрировать её.
- **Приёмка:** сценарий: объект без готового Lean-паттерна проходит через достройку и валидируется; новая стратегия осталась в реестре для повторного использования.

### 5.3 Пилот переноса на другой домен
- **Мотивация:** проверить обобщённость архитектуры на практике.
- **Что сделать:** минимальный второй `DomainPack` (например, формализация в другом целевом языке/нотации на небольшом корпусе) как доказательство переносимости.
- **Приёмка:** второй домен проходит экстракцию→промоушен→валидацию end-to-end на мини-корпусе, переиспользуя ядро без его правок.

**Выход Этапа 5:** ядро домен-агностично; есть механизм достройки представлений; переносимость подтверждена пилотом.
